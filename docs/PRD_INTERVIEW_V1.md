# Eato V1.0 · 产品需求与验收（面试作品版）

**版本**：Interview MVP 1.0 · 2026-10-27
**状态**：面试演示版已提出实现 PR，未完成线上验收；真实协作版本待验证
**产品定位**：让多人约饭从重复群聊决策，收敛为可解释、可确认的方案。

## 一、要解决的问题

**问题陈述（待实证验证的产品假设）**：18–28 岁朋友小组在「约时间—定餐厅—比优惠」时，信息分散于群聊、社交平台和外卖/团购 App；各人作息、口味和预算有分歧，最终方案难以形成共识。

**成功定义**：一名无上下文的使用者能独立发起一场三人约饭，明确谁何时有空、个人偏好、候选价格依据、分歧和最终方案；不会误把模拟数据当作真实商品报价。

**用户角色**：
- 发起者：给候选、收集反馈、最终确认。
- 参与者：标记时间、偏好与投票，看到可解释结果。
- 作品评审/面试官：不需要真实好友或账号即可完整试用。

**价值假设**：结构化填写和规则聚合可降低群聊往返与跨平台切换；该收益尚无实测数据，不在简历中写作已验证的量化效果。

## 二、核心决策流程

问题 → 设定约饭范围/人均预算 → 收集成员时间及口味 → 汇集餐厅候选 → 规则排序（说明理由和缺失数据） → 投票/否决 → 确认时间和餐厅 → 留存结果。

### 最小端到端体验：五个触点

| 触点 | 用户操作 | 可验收结果 |
| --- | --- | --- |
| 进入 | 打开面试演示地址 | 不登录、不输入隐私信息即可进入示例 |
| 时间 | 切换成员、开关日期时段 | 全员共同时间动态改变；缺席时不可确认 |
| 偏好 | 更改成员喜欢的菜系 | 分项口味得分与选项排序可解释地变化 |
| 候选 | 查看餐厅、参考价和冲突项 | 演示价格明确标注，距离/历史缺失不伪装为真实数据 |
| 共识 | 选择成员投票，否决再支持，确认 | 否决阻止确认；满足规则后生成清晰最终结果 |

### 规则与边界

当前复用现有领域规则：
- 时间 35%、菜系 25%、预算 15%、距离 15%、历史信号 10%。
- 全员共同可用时间为确认的硬约束；任一参与者对该候选的否决阻止确认。
- 缺失距离、历史数据按中性分，并向使用者明示。评分为**规则解释**，不是 AI 生成结论。

首版暂缓：真实支付、真实实时比价、无授权平台抓取、微信登录、长期运营数据、完整地图路径规划。真实跨设备协作另行基于云端访客 + Supabase + RLS 验收，不能由模拟体验推断已经成功。

## 三、交互与异常处理

- 页面加载：有明确加载状态，不白屏；主页面与 demo 独立路由。
- 缺失数据：没有时段则提示填写；缺少实时距离或历史则展示中性分警示。
- 无共同时间：方案可看，但确认按钮不可用。
- 否决冲突：显示否决阻止确认；可修改投票恢复。
- 不依赖云端配置：面试 demo 不要求密钥或好友在线；在线真实协作失败不能假装已同步。
- 重置：一键恢复固定场景，便于面试重复操作。
- 小屏：按钮可点击，不发生遮挡或横向溢出。
- 价格：区分虚构参考价、用户输入报价与真实授权接口数据，并标记来源/更新时间。

## 四、五个核心埋点设计（设计稿，非已部署数据采集）

| 事件名 | 触发时机 | 核心属性（不含个人身份信息） |
| --- | --- | --- |
| demo_open | 面试页首次展示 | entry=demo, app_version |
| availability_changed | 任一时段开关 | participant_index, meal_period, selected |
| preference_changed | 偏好切换 | participant_index, cuisine |
| candidate_voted | 支持/否决 | candidate_key, vote_value |
| plan_confirmed | 决策成功 | candidate_key, option_rank, has_full_availability |

**隐私约束**：不采集姓名、邮箱、精确定位、第三方账户凭证；正式接入埋点前另行完善隐私声明和合规确认。设计了事件 ≠ 已上报分析平台。

建议分析漏斗：demo_open → availability_changed / preference_changed → candidate_voted → plan_confirmed。由于演示样本非真实用户，不用此漏斗的数据推断市场效果。

## 五、验收规则（交付前必须逐项验证）

| 类别 | 验收条件 | 当前证据 |
| --- | --- | --- |
| 单人试用 | 无痕浏览器打开线上链接，90 秒左右完成核心流程 | 待线上测试 |
| 逻辑 | 时间改变影响可确认状态；否决后按钮禁用；支持后可确认 | 已添加自动化测试，待 CI 结果 |
| 体验 | 375px 手机端，无溢出，键盘可操作，恢复状态可理解 | 待人工测试 |
| 性能 | 主流程可交互时间目标不超过 3 秒；失败时需明确降级和重试策略 | 目标，尚未实测，不应对外称已达成 |
| 价格可信 | 无伪造实时优惠或无来源最低价 | demo 无任何实时比价接入 |
| 回归 | 原首页及生产 App 不受本功能更改；CI 测试/构建通过 | 仅新增独立路由；CI 待验 |
| 安全 | 无服务端密钥入前端包；不存在真实账号强制注册 | demo 不用云端 |
| 作品真实性 | PRD、原型、Git 提交和线上状态可一一对应 | PRD 和 Git 提交可查；Figma/线上需另行核验 |

## 六、验收资料包（最终给面试官）

1. **一个独立可访问的演示网址**（第一优先级）。
2. 两分钟体验指南（简短，不要求看技术文档）。
3. 本 PRD 的链接，突出问题定义、MVP 取舍、核心规则及异常状态。
4. Figma 原型链接及「原型 → 实现」对照截图（尚待确认正确版本）。
5. GitHub 可审阅的源码/PR 与测试记录。
6. 一页迭代复盘：哪些完成、哪些是演示、有哪些待补数据/风险。

## 七、简历表述审校原则

- 能证明的：独立做出面向多人约饭决策的交互演示，复用规则评分和投票确认，编写需求/验收与自动化测试。
- 需要再证明的：真实跨设备多人协作上线、第三方优惠数据有效性、3 秒超时降级实测、线上真实埋点、Figma 原型逐页还原。
- 不要将“预计提升”“设计了”“Mock 展示”改写成“已提高”“已上线”“实时获取”。
