# Eato：竞品、用户痛点和体验迭代研究（2026-10-27）

## 0. 核心判断

**定位假设**：Eato 不再把“全能美食推荐/比价”作为第一卖点，而是帮助既有朋友群体以最低沟通成本达成一次可执行的聚餐共识。

**必须证伪的问题**：用户会不会宁愿继续用微信群/大众点评/美团，也不愿为一个并不高频的约饭场景打开新网页？

本报告采用“外部观察 → 假设 → 设计方向 → 验证方式”的格式。下述研究说明的是潜在需求，**不是 Eato 已被证明有市场**。

## 2. 竞争边界

- **微信/群聊**：用户已有触达，交流零迁移；缺点是结构化候选和最终结论难持久整理。Eato 必须与群聊共存，不能要求用户换通讯工具。
- **Doodle/When2meet/一起约**：解决时间/投票；缺少或未突出餐饮场景特有的口味/忌口/预算/候选店来源。Eato 用“时间 + 店 + 预算 + 共识”的可解释输出竞争。
- **大众点评/美团/小红书/抖音**：餐厅供给与评价可信度强，Eato 不应竞逐全量供给。使用用户分享的原始链接，并导回原平台核验交易。
- **鸭觅等口味推荐**：偏向个人匹配/探索。Eato 的机会是“多人群体下的冲突透明化”，不能依赖黑箱评分掩盖有人无法参加或忌口。

## 3. 待验证的用户画像与 JTBD

| 角色 | JTBD | 最小成功体验 |
| --- | --- | --- |
| 约饭发起人 | 我要约 3-6 个熟人一起吃饭，不想在群里催回复、反复问地点 | 90 秒内创建链接；看到已回复/未回复和下一步建议 |
| 普通朋友 | 我愿意参加，但不想下载 App/注册/填长表 | 点开微信转发链接，最多 3 个核心操作：能否到、忌口、可否接受餐厅 |
| 有特殊限制的成员 | 我的预算、忌口、行动距离是必须被尊重的条件 | 无合规方案时给出真实冲突，不做“少数服从多数”硬覆盖 |
| 面试官 | 我不了解 Eato，但想快速判断产品思考与实际交互能力 | 独立 90 秒复现从协调到确认，知道什么是模拟与非模拟 |

**预设用户区间**：18-28 岁仅用于首轮研究招募；不要把它误写为已验证 PMF 人群。

## 4. 按用户任务重新设计信息架构

1. **发起**：只问大致日期、参与人数（可跳过预算/地点）；首次创建不需要“城市、区域、预算上下限、所有成员昵称”的长表。
2. **邀请与回答**：微信群可复制的短链接；参与者默认免注册；先给“能来/待定/不能来”，再按需求补时段、口味与忌口。
3. **已有餐厅输入**：粘贴美团/点评/小红书分享链接或手动填店名；保留来源，未授权/解析失败时不要瞎补店铺字段。
4. **聚合**：呈现“全员可行 / 少一人 / 待补资料”，对忌口、预算硬限制直接标注，不用一个抽象总分盖掉冲突。
5. **决定**：三张候选方案卡，支持/勉强/否决；无需必须投满所有店；到截止时间可由发起者发出“一次确认卡片”。
6. **结果**：输出群聊可复制的时间、人数、地点、参考预算、未确认风险、验证链接；不声称已完成线上订座/支付。

## 5. 团体推荐算法的改造建议（单独版本验证，不直接改现有生产引擎）

现有规则权重：时间 35%、菜系 25%、预算 15%、距离 15%、历史 10%。当前代码：
- 将所有「餐厅×日期时段」评分后截取前三，可能导致同一家餐厅在不同时段占据多个结果位置；
- 未达到全员可参加的方案仍可能因总分较高排到第一；
- 投票否决影响确认按钮，但候选排序没有解释“为什么有人否决”；
- 距离/历史缺失给 50 中性分，面试官可能将结果误认为实际出行最优；
- 某成员完全不回复时缺少催回复、候选备用日期和最终协调机制。

提出一套更可解释的约束优先级：
A. **先过滤硬约束**：忌口/过敏（须显式区分）、预算上限、闭店、无法到达；未知条件标「待核实」而非默认可行。
B. **再列团体可达性**：全员、接近全员、无人可行；业务上是否允许“少一人”应由发起者和成员确认。
C. **最后软排序**：口味、位置、公平度/历史轮换、优惠可信度；各因子显式显示，不给不可比数据伪精准百分制。
D. **聚合的可读性**：首页优先展示 2-3 家不同餐厅；每家可展开备选日期，而非一个店刷屏。
E. **失败前进路径**：没有满足硬约束的选项时明确“谁的限制未满足 + 能怎么改”，不暗中牺牲偏好。

## 6. 研究设计与验收指标

**第一轮定性访谈（建议 10-12 人）**：4 名常见发起者、4 名普通参与者、2-4 名低响应或带约束者。要求对方讲最近一次真实聚餐的聊天/决策经过，而非询问“你喜欢这个功能吗”。征得同意后记录自然发生的打断、搜索、确认动作，不保存无关私人聊天。

**两种低成本可用性实验**：
- A：微信临时群聊 + 现有投票功能完成一场模拟约饭。
- B：Eato 原型完成同一场景，比较任务完成时间、操作/跳转次数、未答复人数、决策是否满足忌口和共同时间。样本小，只用于发现问题，不用来宣称统计显著性。
- 另测试两组多人用户是否真的愿意把链接发进微信群并完成一次协作，区分“看起来有用”和“会实际使用”。

**第一阶段拟定成功门槛（产品目标，未经测量）**：

| 指标 | 暂定验收目标 | 必须如何测量 |
| --- | --- | --- |
| 面试官体验成功率 | 5/5 独立完成核心闭环 | 5 名不熟悉项目的人自行操作 |
| 首次创建成本 | 不超过 60 秒 | 从打开到获得邀请链接的任务计时 |
| 受邀者响应成本 | 不超过 30 秒 | 从打开链接到完成核心输入 |
| 数据真实性 | 0 次误导性实时报价声明 | 手动复核每处价格、来源、更新时间 |
| 方案执行性 | 0 次违反已知强制约束 | 自动化硬约束案例覆盖 |
| 渐进式披露 | 不要求填写非必要字段才能进入核心体验 | 观察每个首次交互步骤 |

最终要在简历展示**实测结果**，例如“测试 5 人，其中 4 人独立完成”，而不是提前写成已经提升多少百分比。

## 7. 迭代计划与范围控制

- **P0 · 可交付面试作品**：无账户 Demo、三人示例、时间/偏好互动、冲突及原因、规则排序、否决与确认、能独立复现的测试和线上部署。
- **P1 · 有价值的真实多人 MVP**：微信分享链接、免注册回答、状态恢复、权限保护、群成员响应、冲突与兜底、确认卡片。
- **P2 · 餐厅情境能力**：候选链接导入、来源和更新时间、位置/时段的真实约束，价格可靠性声明。
- **P3 · AI/商业化**：有授权的数据源后再研究实时价格；AI 生成冲突总结/理由/候选，而非虚构优惠；通过真实用户行为验证留存与传播后再考虑变现。

**原则**：先证明有人愿意用，再论证 AI 和商业化；先补最终链接和 PRD 证据链，再增加非核心功能。
