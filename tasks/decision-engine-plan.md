# `decision-engine` 实施计划

对应规格：[SPEC-decision-engine.md](../SPEC-decision-engine.md)。本模块仅使用纯函数计算饭局候选方案；不读取本地存储、不调用 AI、不改 UI。

## 设计决定

1. `DecisionContext` 只携带可选的距离与历史输入；没有数据时显式用中性分并写入冲突提示。
2. 先为每个候选枚举已选时间段，形成“候选 × 时间”的方案；完整交集优先，缺少交集时仍返回冲突最少的协调建议。
3. 所有硬约束在评分前过滤：忌口匹配、明确人均预算上限。被排除的候选不进入前三。
4. 评分分项与权重以导出常量保存；总分四舍五入到一位小数。
5. 排序稳定：总分 → 是否可确认 → 预算分 → 候选 ID / 时间，确保相同输入可复现。

## 实施顺序

1. 建立决策输出类型和权重常量。
2. 用失败测试定义硬忌口、预算上限和完整时间交集。
3. 实现最小过滤与时间匹配。
4. 用失败测试定义加权评分、无共同时间与稳定排序。
5. 实现评分、理由、冲突披露与前三限制。
6. 运行全量回归与构建。

## 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 没有共同时间仍被错误确认 | `readyToConfirm` 只能在全员可用时为 true；测试覆盖此情形。 |
| LLM 影响确定性决策 | 本期不导入任何 AI Provider；输出只提供结构化理由。 |
| 距离/历史缺失被伪装为真实数据 | 统一采用 50 分中性值并放入 `conflicts`。 |
| 评分逻辑难以复核 | 导出分项和权重，测试直接断言结果。 |
