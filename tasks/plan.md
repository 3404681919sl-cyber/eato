# `meal-domain` 实施计划

对应规格：[SPEC-meal-domain.md](../SPEC-meal-domain.md)。本计划只实现第一阶段的领域模型；不接入存储、不改页面、不新增依赖。

## 设计决定

1. 新模型放在 `src/domain/meal.ts`，不混入现有 `Place`、`Visit` 与旧打卡数据类型，避免破坏已可运行的功能。
2. 领域模型只依赖 TypeScript 标准能力；所有校验和状态推进都是同步纯函数，便于单测和未来服务端复用。
3. 用户输入错误统一返回 `DomainIssue[]`，让 UI 直接显示中文提示，而不是靠抛异常控制流程。
4. 时间采用 `YYYY-MM-DD` 加受控餐段（`lunch` / `afternoon` / `dinner`），本期不引入时区或原生日历权限；真实同步阶段再处理。
5. `MealEvent` 聚合保存当前饭局的成员和其提交，后续数据库拆表时由 Repository 完成映射，页面不感知变化。

## 实施顺序与检查点

### 1. 领域骨架

创建类型、枚举和受控常量；只导出后续模块真正需要的业务对象。

- 检查点：类型检查可通过；现有代码不需要改动。

### 2. 输入校验

测试并实现创建饭局、预算、成员数量和候选优惠数量校验。

- 检查点：先观察测试因缺少校验函数而失败，再以最小纯函数通过。

### 3. 状态机

测试并实现合法的饭局状态迁移及“确认后退回收集”的特例。

- 检查点：非法跳转保持原状态并返回明确错误；合法跳转返回新对象而不修改入参。

### 4. 回归

运行领域测试、全量测试和生产构建。

- 检查点：无新增依赖；既有测试仍全部通过。

## 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 新领域对象与旧打卡模型混淆 | 使用独立 `src/domain/`，不修改既有 `src/types/index.ts`。 |
| 本地模拟的结构难以迁移到真实库 | 使用稳定 ID、扁平字段和 Repository 边界；不把 `localStorage` 细节放进领域类型。 |
| 规则范围膨胀到 UI/AI | 本模块只建立契约和校验；评分与理由留给 `decision-engine`。 |
